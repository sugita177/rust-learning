# 03_borrowing: 借用と参照（Borrowing & References）

Rust の最大の特徴であるメモリ安全性を保ちながら、所有権をムーブさせずにデータを効率よく利用・変更するための「参照（Reference）」と「借用（Borrowing）」、および借用チェッカー（Borrow Checker）のルールについて学ぶ演習です。

---

## 実行コマンド

```bash
# 借用演習バイナリの実行
cargo run -p borrowing

# コンパイルチェック
cargo check -p borrowing
```

---

## 1. 基本事項・概念の整理

### 1.1 なぜ「借用（Borrowing）」が必要なのか？
前章（`02_ownership`）で学んだ通り、関数に値を渡すと所有権がムーブ（移動）してしまい、呼び出し元では二度と使えなくなります。
関数呼び出し後も呼び出し元で再利用したい場合、毎回タプル `(s, result)` のようにして所有権を返却してもらう必要があり、コードが非常に冗長になります。

これを解決するのが **「参照（Reference: `&`）」による「借用（Borrowing）」** です。
- **所有権は元の変数が保持したまま**、データへのアクセス権（ポインタ）のみを貸し出す。
- 参照を受け取った側は所有者ではないため、関数を抜けても **ヒープ領域のデータは Drop（解放）されない**。

### 1.2 メモリモデル：参照（ポインタ）の実態
参照 `&String` は、メモリ上（スタック）では単なる **「8バイトのポインタ（メモリアドレス）」** です。

```text
【呼び出し元スタック（main）】           【ヒープ領域】
s1 (所有者: 合計24バイト)
┌──────────┬─────────────────┐
│ ptr      │ 0x10111d8f0 ────┼───► [ 'H', 'e', 'l', 'l', 'o' ]
├──────────┼─────────────────┤
│ len      │        5        │
├──────────┼─────────────────┤
│ capacity │        5        │
└──────────┴─────────────────┘
      ▲
      │ 0x16f47dbd8（s1のアドレスを格納）
【関数側スタック（get_length）】
s_ref (参照: 8バイト)
┌──────────┬─────────────────┐
│ ptr      │ 0x16f47dbd8     │
└──────────┴─────────────────┘
(自身のアドレス: 0x16f47d928)
```
- `s_ref` 自体は `get_length` のスタックフレーム上に置かれた 8 バイトの変数（アドレス: `0x...928`）。
- その中身は `s1` のスタックアドレス（`0x...bd8`）。
- `s1` の内部ポインタが指す先がヒープ実データ（`0x10111d8f0`）。

### 1.3 可変参照（`&mut`）
- **定義**: 参照先（借用したデータ）を直接書き換える権限を持つ参照。
- **条件**:
  - 元の変数自身が `mut` で宣言されている必要がある（`let mut s = ...;`）。
  - 借用する際にも `&mut s` と明示し、受ける側も `&mut String` と型指定する。
- **挙動**: 所有権を奪うことなく、ヒープ実データを安全に直接編集（`push_str` など）できる。

### 1.4 借用チェッカーの「2大絶対ルール」
Rust コンパイラ（借用チェッカー）は、データ競合（Data Race）やメモリ安全性の破壊をコンパイル時に完全に防ぐため、以下の2つの絶対ルールを強制します。

1. **排他制御のルール（同時に存在できる参照の制限）**:
   - あるデータに対して、同時に存在できるのは以下の **どちらか一方のみ** である。
     - **任意の数の不変参照（`&T`）**（読書中は何人同時に覗いても安全）
     - **たった1つの可変参照（`&mut T`）**（書き換える人がいるなら、他者は読むことも書くことも禁止）
2. **参照の有効期間のルール（ダングリング参照の防止）**:
   - **参照は、常に指している先（データ本体）よりも長生きしてはならない。**

### 1.5 NLL（Non-Lexical Lifetimes: 非レキシカルスコープのライフタイム）
- Rust 2018 以降導入された洗練された借用解析機構。
- 従来の言語のように「中括弧 `{ }` の終端まで」参照が有効とみなされるのではなく、**「その参照が最後に使われたコード行（Last Use）」** で借用期間が終了したと判定される。
- これにより、「不変参照を使った後、同じスコープの後の行で可変参照を作る」といった自然で安全なコードが柔軟に書けるようになっている。

## 2. 学び・検証記録（エラー体験とメモリアドレス検証）

### 2.1 [メモリ検証] 不変参照の3層アドレス構造
- **検証コード**:
  ```rust
  fn get_length(s_ref: &String) -> usize {
      println!("s_refが指す先のアドレス: {:p}", s_ref);
      println!("s_ref自身のスタックアドレス: {:p}", &s_ref);
      println!("ヒープアドレス: {:p}", s_ref.as_ptr());
      s_ref.len()
  }
  ```
- **実行結果**:
  ```text
  s1自体のメモリアドレス:                        0x16f47dbd8
  get_length内での引数（s_refが指す先）のアドレス: 0x16f47dbd8
  get_length内での引数（s_ref自身）のスタックアドレス: 0x16f47d928
  ヒープ領域にある引数が指す領域のアドレス:        0x10111d8f0
  ```
- **実証できたこと**:
  - `s_ref` 自体はスタックフレーム上に独立して確保された 8 バイトの箱（`0x...928`）である。
  - `s_ref` が格納している値は `s1` のスタック番地（`0x...bd8`）と完全に一致している。
  - 関数終了後も `s1` は有効なままであり、所有権が奪われていないことが実証された。

### 2.2 [メモリ検証] 可変参照（`&mut`）によるヒープ実データの安全なインプレース更新
- **検証コード**:
  ```rust
  fn change_str(s_ref: &mut String) {
      s_ref.push_str(", world");
  }
  ```
- **実行結果**:
  ```text
  s2（変更前）のメモリアドレス: 0x16f47dd28, ヒープ: 0x10111d900
  s2 after change_str: Hello, world
  s2（変更後）のメモリアドレス: 0x16f47dd28, ヒープ: 0x10111d900
  ```
- **実証できたこと**:
  - `s2` のスタックアドレスおよびヒープアドレスは変更前後で **完全に同一のまま**、中身の文字列のみが更新された。
  - 重い再確保や所有権のバトンリレーなしに、安全にインプレース（その場）変更が行われた。

### 2.3 [コンパイルエラー] 可変参照の多重借用（E0499）とデータ競合防止
- **コード**:
  ```rust
  let mut s3 = String::from("Rust");
  let r1 = &mut s3;
  let r2 = &mut s3; // ← エラー！
  println!("{}, {}", r1, r2);
  ```
- **発生したエラー**:
  ```text
  error[E0499]: cannot borrow `s3` as mutable more than once at a time
    --> exercises/03_borrowing/src/main.rs:52:14
     |
  51 |     let r1 = &mut s3;
     |              ------- first mutable borrow occurs here
  52 |     let r2 = &mut s3;
     |              ^^^^^^^ second mutable borrow occurs here
  53 |     println!("r1: {}", r1);
     |                        -- first borrow later used here
  ```
- **なぜコンパイラが防ぐのか（何が危険なのか）**:
  - もし `r1` が文字列を追加してヒープ領域の再割り当て（リロケーション）を起こした場合、古いヒープは解放される。
  - その場合、`r2` はすでに解放された無効なメモリを指すことになり、**ダングリングポインタ（Use After Free）** になる。
  - Rust は可変参照を常に 1 人だけに制限することで、この危険を根絶している。

### 2.4 [コンパイルエラー] 不変参照と可変参照の同居禁止（E0502）
- **コード**:
  ```rust
  let mut s4 = String::from("Cargo");
  let r4 = &s4;
  let r5 = &s4;
  let r6 = &mut s4; // ← エラー！
  println!("{}, {}, {}", r4, r5, r6);
  ```
- **発生したエラー**:
  ```text
  error[E0502]: cannot borrow `s4` as mutable because it is also borrowed as immutable
  ```
- **なぜコンパイラが防ぐのか（何が危険なのか）**:
  - `r4` や `r5` の利用者は「データは変わらない（不変）」と信じて読み取っている。
  - その背後で `r6` がデータを勝手に書き換えてしまうと、データ不整合やメモリ再配置によるクラッシュが起きる。
  - 「読み手がいる間は、書き手は割り込めない」という排他制御をコンパイル時に保証している。

### 2.5 [NLLの実証] 借用期間の自動終了
- **実証コード**:
  ```rust
  let r1 = &mut s3;
  println!("r1: {}", r1); // r1 の最後の使用箇所！
  
  // r1 のライフタイムが終了したため、新しく r3 を作れる！
  let r3 = &mut s3;
  println!("r3: {}", r3);
  ```
- **学び**:
  - `r1` の寿命が `println!` で完了したことをコンパイラが検知するため、エラーにならず安全に次の可変参照 `r3` を作成できる。

### 2.6 [コンパイルエラー] ダングリング参照の防止（E0106）
- **コード**:
  ```rust
  fn dangle() -> &String {
      let s = String::from("dangle");
      &s // ローカル変数の参照を返そうとする
  }
  ```
- **発生したエラー**:
  ```text
  error[E0106]: missing lifetime specifier
    --> exercises/03_borrowing/src/main.rs:18:16
     |
  18 | fn dangle() -> &String {
     |                ^ expected named lifetime parameter
     |
     = help: this function's return type contains a borrowed value, but there is no value for it to be borrowed from
  help: instead, you are more likely to want to return an owned value
     |
  18 - fn dangle() -> &String {
  18 + fn dangle() -> String {
     |
  ```
- **なぜコンパイラが防ぐのか**:
  - 関数内で生成されたローカル変数 `s` は、関数の終わり（`}`）でスコープを抜けてヒープ領域ごと Drop（メモリ解放）される。
  - その参照を返すと、呼び出し元は「すでに解放されたメモリ」を覗くことになり致命的なバグになる。
  - Rust は引数がないのに関数から参照を返そうとするコードを即座に拒否する。
- **解決策**:
  - コンパイラの助言通り、参照ではなく **所有権そのもの（`String`）を直接返す（`no_dangle`）**。
  - 所有権のムーブにより、メモリは破棄されず安全に呼び出し元へ引き継がれる。
