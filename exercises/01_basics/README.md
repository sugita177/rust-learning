# 01_basics: 基本文法と変数

Rust の基本文法、変数の不変性（デフォルト）と可変性（`mut`）、シャドーイング、基本データ型について学ぶ演習です。

```bash
# テスト実行

```

## 1. 基本事項・概念の整理

### 不変性（`let`）と可変性（`let mut`）
- **束縛（Binding）**: Rust では変数への値の割り当てを「束縛」と呼ぶ。
- **デフォルトは不変（immutable）**: `let x = 5;` のように宣言した変数は後から再代入できない。
- **可変にするには `mut`**: 再代入が必要な場合のみ `let mut y = 5;` と明示する。
- **なぜデフォルト不変なのか**: 意図しない値の書き換えバグを防ぎ、マルチスレッド環境でも安全にするため。

### 変数の束縛とメモリ（スタック領域）の実態
- `let x = 5;` と宣言したとき、メモリ上（スタック領域）には値 `5`（4バイト整数 `i32`）が直接格納される。
- `x` はそのメモリ番地につけられたラベル（目印）。
- `&x` はそのメモリ番地（先頭アドレス）そのものを指す（`{:p}` で表示可能）。

### シャドーイング（Shadowing）
- **定義**: 同じスコープ内で、既に存在する変数名と同じ名前を使って、再度 `let` で新しい変数を宣言すること。
- **`mut`（再代入）との決定的な違い**:
  - **メモリアドレスの挙動**:
    - `mut`: **同じアドレス** の中身を上書きする。
    - シャドーイング: スタック上に **まったく新しいアドレス** を確保して同じ名前を付け直す（前の変数を覆い隠す）。
  - **不変性の維持**: 計算や加工を行った後も、変数を不変（immutable）のまま保てる。
  - **型の変更が可能**: `let mut` では型を変えられないが、シャドーイングなら新しい箱を作り直すため型を変えられる（例: 数値から文字列 `"hello"` へ）。
- **スコープ（`{}`）とシャドーイング**:
  - ブロックの内側でシャドーイングされた変数は、ブロック内でのみ有効。
  - ブロックを抜けると内側の変数はスコープを外れて破棄され、外側の変数が再び参照される。
- **同じスコープでのメモリ解放タイミング（RAII）**:
  - 同じスコープ内でシャドーイングされた場合、前の値へのアクセス権（ラベル）は失われるが、**その瞬間にメモリが即座に解放されるわけではない**。
  - Rustの基本原則として、メモリの解放は「その変数が宣言されたスコープ（`{ }`）の終端」に到達した際に行われる。
  - そのため、スコープが終了するまでは物理的にメモリ（スタック領域やヒープ領域）に残る点に注意。

## 2. 学び・詰まったポイント（エラー体験と解決策）

### 1. `cargo new` でパッケージ名が数字から始められない
- **やりたかったこと**: `exercises/01_basics` というディレクトリ名でパッケージを作成しようとした
- **発生したエラー**:
  ```text
  error: invalid character `0` in package name: `01_basics`, the name cannot start with a digit
  note: the directory name is used as the package name
  help: to override the package name, pass `--name <pkgname>`
  ```
- **原因**:
  - Rust の識別子（クレート名・パッケージ名）は、C言語などと同様に「数字から始めることができない」命名規則がある。
  - `cargo new` はデフォルトで作成先ディレクトリ名をそのままパッケージ名に採用しようとするため。
- **解決法**:
  - ディレクトリ名は整理のため `01_basics` としつつ、`--name basics` を指定してパッケージ名だけ英字始まりにする。
  ```bash
  cargo new --bin --vcs none --name basics exercises/01_basics
  ```

### 2. 不変変数への再代入でコンパイルエラー（E0384）
- **コード**: `let x = 5; x = 6;`
- **エラー**: `cannot assign twice to immutable variable x`
- **学び**: コンパイラが親切に `let mut x = 5;` を提案してくれる。未使用の代入に対する warning も検知してくれる。

### 3. メモリアドレスを出力して確認した mut とシャドーイングの挙動の違い
- **確認方法**: `println!("{:p}", &変数)` で変数が置かれているスタック上のメモリアドレスを表示。
- **結果**:
  - `mut` で値を `5` から `6` に変更した場合: **アドレスは同一** のまま、データだけが書き換わる。
  - シャドーイングを繰り返した場合: 毎回 **異なる新しいアドレス** が割り当てられている。
  - スコープ `{}` 内でのシャドーイング: 内側では新しいアドレスが使われ、スコープを抜けると自動的に外側のアドレス（元の値）に戻る。
- **学び**: 
  - 「同じ名前を再利用している」だけで、ハードウェアレベルでは全く別のメモリ領域を使っていることが視覚的に理解できた。

### 4. Drop トレイトによる「シャドーイング時のメモリ解放タイミング」の実証（`src/bin/drop_check.rs`）
- **疑問**: 同じスコープでシャドーイングした場合、前の値は即座に解放されるのか？
- **検証方法**:
  - メモリ解放時にメッセージを出力する `Drop` トレイトを実装した構造体 `Inspector` を作成。
  - `src/bin/drop_check.rs` に検証コードを配置し、同じスコープでシャドーイングを実施。
- **実行結果**:
  ```text
  --- シャドーイングとメモリ解放の実験開始 ---
  1番目のaを作成しました
  a.nameの値 : 1st a
  2番目のaを作成しました
  a.nameの値 : 2nd a
  まだスコープの中にいます
  [Drop実行]2nd a is が解放されました!
  [Drop実行]1st a is が解放されました!
  スコープを抜けました
  ```
- **学び・実証できたこと**:
  - `2nd a` でシャドーイングされた後も、「まだスコープの中にいます」の時点では `1st a` は **一切解放されていない**。
  - スコープの終端（`}`）に到達した瞬間に、定義された逆順（LIFO: 後入れ先出し）で `2nd a` → `1st a` の順にまとめて解放された。
  - これにより、「シャドーイングは変数を即時破棄するのではなく、スコープ終了までメモリ上に残り続ける」ことが完全に実証された。
  - ※なお、`Drop` トレイトの `drop` メソッドは「メモリ物理解放直前のコールバック（前処理）」であり、メソッド実行後にコンパイラが自動で物理メモリを確実に解放するため、メモリリークの心配はない。
