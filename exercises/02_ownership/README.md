# 02_ownership: 所有権（Ownership）

Rust の最大の特徴であり、ガベージコレクタ（GC）なしでメモリ安全性をコンパイル時に保証するコア機能「所有権（Ownership）」、ムーブセマンティクス、クローン、コピー、関数とのやり取り、そしてスコープと Drop の挙動について学ぶ演習です。

---

## 実行コマンド

```bash
# 所有権演習バイナリの実行
cargo run -p ownership

# コンパイルチェック
cargo check -p ownership
```

---

## 1. 基本事項・概念の整理

### 1.1 所有権の「3大ルール」
Rust のすべてのメモリ管理は、以下の3つの絶対ルールに基づいています。

1. **Rust の各値は、「所有者（Owner）」と呼ばれる変数を持つ。**
2. **いかなる時点でも、所有者は常に「1人（1つの変数）」だけである。**
3. **所有者がスコープ（`{ }`）を抜けると、その値は自動的に破棄（メモリ解放: Drop）される。**

### 1.2 メモリモデル：スタック（Stack）とヒープ（Heap）
所有権の挙動（特にムーブ）を理解する鍵は、メモリ領域の使い分けにあります。

- **スタック領域**:
  - コンパイル時にサイズが確定している固定長データを格納。
  - 高速に割り当て・解放が行われる（LIFO: 後入れ先出し）。
  - 例: `i32`, `bool`, 固定長配列、ポインタやメタデータ。
- **ヒープ領域**:
  - 実行時に動的にサイズが変わる可変長データや大きなデータを格納。
  - OSに空き領域を要求して確保するためスタックよりコストがかかる。
  - 例: `String`, `Vec<T>`。

#### `String` 型のメモリ構造
`let s1 = String::from("hello");` と宣言した場合、メモリ上では次のように配置されます。

```text
【スタック領域（s1: 合計24バイト）】      【ヒープ領域】
┌──────────┬─────────────────┐
│ ptr      │ 0x100325910 ────┼───► [ 'h', 'e', 'l', 'l', 'o' ]
├──────────┼─────────────────┤
│ len      │        5        │
├──────────┼─────────────────┤
│ capacity │        5        │
└──────────┴─────────────────┘
```
- **スタック上**: ヒープへのポインタ（8バイト）、現在の長さ `len`（8バイト）、確保容量 `capacity`（8バイト）の合計24バイト。
- **ヒープ上**: 実際の文字列データ本体（バイト列）。

### 1.3 ムーブセマンティクス（所有権の移動）
- **定義**: ある変数から別の変数へ値を代入した際、データそのものを複製するのではなく、**所有権そのものが新しい変数へ移り、元の変数が即座に無効化される** 挙動。
- **浅いコピー（Shallow Copy）との違い**:
  - 一般的な言語の浅いコピーではポインタのみを複製するため、参照元が2つになり「二重解放（Double Free）」やデータ競合のリスクが生じる。
  - Rust ではスタック上の24バイトをコピーした直後に **元の変数（`s1`）を無効化（使用不可）** することで、常に所有者を1人に保つ。

### 1.4 クローン（`Clone` トレイト）
- **定義**: ヒープ領域のデータも含めて、丸ごと新しいメモリ領域へ複製する「ディープコピー」。
- **特徴**:
  - 明示的に `.clone()` メソッドを呼び出す必要がある。
  - ヒープのメモリ再確保とデータコピーを伴うため、実行時コスト（時間・メモリ）がかかる。
  - 複製後は元の変数も新しい変数もそれぞれ独立した所有権を持つため、両方とも有効なまま利用できる。

### 1.5 コピー（`Copy` トレイト）
- **定義**: 代入（`let y = x;`）時に所有権が移動せず、スタック上のビット列が自動的に複製される挙動。
- **ムーブとコピーの分かれ目**:
  - **`Copy` が実装されている型**:
    - コンパイル時にサイズが既知で、スタック上だけで完結する型（`i32`, `f64`, `bool`, `char`, `Copy` な型のタプル・配列など）。
    - 外部リソース（ヒープメモリやファイル記述子など）を所有しておらず、破棄時のクリーンアップ処理（`Drop` トレイト）が必要ない型。
  - **`Copy` が実装されていない型**:
    - ヒープメモリを所有する型（`String`, `Vec<T>` など）。代入すると自動的にムーブになる。

### 1.6 関数と所有権（引数と戻り値）
- **引数の受け渡し**: 変数への代入と全く同様のセマンティクスが適用される。
  - `Copy` な型（`i32` など）を渡すと、関数の仮引数に値がコピーされ、呼び出し元の変数は引き続き有効。
  - `Copy` でない型（`String` など）を渡すと、関数の仮引数へ所有権がムーブし、呼び出し元の変数は無効化される。
- **関数終了時のメモリ解放**:
  - 関数内で所有権を受け取った変数は、その関数が終了した瞬間にスコープを抜け、メモリ（ヒープ領域）が自動解放（Drop）される。
- **戻り値による所有権の譲渡**:
  - 関数から値を返すと、その値の所有権は呼び出し元の受け取り変数へムーブする。
- **借用（Borrowing）への動機**:
  - 関数に値を渡して処理させたいだけなのに、所有権が奪われて使えなくなるため、毎回戻り値でタプル等にして所有権を返してもらうのは非常に冗長。
  - これを解消するために「所有権を移動させずに中身を参照する」次章の「借用（`&`）」が必要となる。

### 1.7 スコープとメモリ解放（Drop）
- **RAII（Resource Acquisition Is Initialization）の徹底**:
  - リソースの寿命は変数のスコープ（`{ }`）と完全に一致する。プログラマが明示的に `free()` を呼ぶ必要はない。
- **内部スコープ（`{ }`）**:
  - ブロックの内側で宣言された変数は、ブロックを抜けた瞬間に Drop される。局所的に大きなメモリを即座に解放したい場合に有効。
- **ムーブ後の変数の状態（未束縛状態）と Drop の除外**:
  - `let c_after_move = c_before_move;` とムーブした場合、データへの束縛は `c_after_move` に付け替えられ、元の `c_before_move` は **「いかなる値にも束縛されていない未初期化状態」** になる。
  - コンパイラは静的解析により、スコープ終了時の Drop 呼び出しリストから `c_before_move` を完全に除外する。そのため、Drop は新しい所有者 `c_after_move` がスコープを抜ける時の **1回のみ** 実行され、二重解放が絶対に起きない。
- **早期解放 `std::mem::drop` の仕組み**:
  - スコープの終端を待たずに即時解放したい場合は `drop(x)` を呼ぶ。
  - `drop` 関数の内部実装は `pub fn drop<T>(_x: T) {}` という「引数を値渡し（ムーブ）して何もしない空の関数」である。引数に所有権を渡して関数を即座に終了させることで、Rust の通常のスコープアウト機構を利用して破棄を実現している。

## 2. 学び・検証記録（エラー体験とメモリアドレス検証）

### 2.1 [コンパイルエラー] ムーブ後の無効化された値へのアクセス（E0382）
- **コード**:
  ```rust
  let s1 = String::from("hello");
  let s2 = s1;
  println!("s1 = {}", s1);
  ```
- **発生したエラー**:
  ```text
  error[E0382]: borrow of moved value: `s1`
   --> exercises/02_ownership/src/main.rs:6:25
    |
  2 |     let s1 = String::from("hello");
    |         -- move occurs because `s1` has type `String`, which does not implement the `Copy` trait
  ...
  4 |     let s2 = s1;
    |              -- value moved here
  5 |     println!("s2 = {}", s2);
  6 |     println!("s1 = {}", s1);
    |                         ^^ value borrowed here after move
    |
  help: consider cloning the value if the performance cost is acceptable
    |
  4 |     let s2 = s1.clone();
    |                ++++++++
  ```
- **学び**:
  - `let s2 = s1;` の時点で `s1` の所有権が `s2` に移動（ムーブ）したため、`s1` は未初期化状態（空っぽ）とみなされる。
  - コンパイラは「すでに所有権を失った変数へのアクセス」を静的解析で完全に弾いてくれるため、実行時に二重解放やクラッシュが起きる余地がない。

### 2.2 [メモリ検証] ムーブ時におけるスタックとヒープのアドレス実態
- **検証方法**:
  - 変数自身のアドレス（`&s1`, `&s2`）と、ヒープを指す内部ポインタのアドレス（`.as_ptr()`）を出力して比較。
- **実行結果**:
  ```text
  s1自体のメモリアドレス: 0x16fb79b28
  ヒープ領域にあるs1が指す領域のアドレス: 0x100325910
  s2自体のメモリアドレス: 0x16fb79bc0
  ヒープ領域にあるs2が指す領域のアドレス: 0x100325910
  ```
- **実証できたこと**:
  - `s1` と `s2` はスタック上で別々のアドレス（24バイトずれた独立した変数枠）に存在する。
  - しかし、両者が指すヒープのアドレスは `0x100325910` で **完全に同一**。
  - これにより、「ムーブとは、ヒープのデータは一切触らず、スタック上のメタデータ（24バイト）のみを高速にコピーし、元の変数へのアクセス権を剥奪する処理である」ことが物理レベルで実証された。

### 2.3 [メモリ検証] クローン（`.clone()`）によるヒープ領域の完全分離
- **検証コード**:
  ```rust
  let s3 = String::from("Good morning");
  let s4 = s3.clone();
  ```
- **実行結果**:
  ```text
  s3自体のメモリアドレス: 0x16fb79c68
  ヒープ領域にあるs3が指す領域のアドレス: 0x100325920
  s4自体のメモリアドレス: 0x16fb79d08
  ヒープ領域にあるs4が指す領域のアドレス: 0x100325930
  ```
- **実証できたこと**:
  - `s3` のヒープ（`0x...920`）と `s4` のヒープ（`0x...930`）で、**完全に別のメモリ番地が確保** されている。
  - ヒープ実データが独立しているため、どちらが先にスコープを抜けてメモリ解放を行っても二重解放にならない。したがって、クローン後は `s3` も `s4` も安全にアクセス可能。

### 2.4 [メモリ検証] コピーセマンティクス（`i32`）におけるスタック上の配置
- **検証コード**:
  ```rust
  let x = 5;
  let y = x;
  ```
- **実行結果**:
  ```text
  x = 5, xのアドレス: 0x16fb79dc0
  y = 5, yのアドレス: 0x16fb79dc4
  x = 5
  ```
- **実証できたこと**:
  - `&x`（`0x...dc0`）と `&y`（`0x...dc4`）の差分は **ぴったり4バイト（`i32` のサイズ）** で、スタック上に隣接して格納されている。
  - ムーブではなくスタック上の値そのものが高速にビットコピーされたため、代入後も `x` の所有権は失われずアクセス可能。

### 2.5 [メモリ検証] 関数呼び出し・戻り値受け渡しにおけるスタックフレームとヒープアドレスの挙動
- **検証コード**:
  ```rust
  fn my_func_return_str(some_string: String) -> String {
      println!("my_func_return_str内での引数のメモリアドレス: {:p}", &some_string);
      println!("ヒープ領域にあるsome_stringが指す領域のアドレス: {:p}", some_string.as_ptr());
      some_string
  }

  // main関数内
  let s2 = String::from("Good morning");
  let s2_returned = my_func_return_str(s2);
  ```
- **実行結果**:
  ```text
  main関数でのs2自体のメモリアドレス:             0x16ee79c78
  ヒープ領域にあるs2が指す領域のアドレス:         0x1018719a0

  my_func_return_str内での引数のメモリアドレス:   0x16ee79d30
  ヒープ領域にあるsome_stringが指す領域のアドレス: 0x1018719a0

  main関数でのs2_returned自体のメモリアドレス:    0x16ee79d18
  ヒープ領域にあるs2_returnedが指す領域のアドレス: 0x1018719a0
  ```
- **実証できたこと**:
  - **スタックフレームによる変数の分離**:
    - `s2`（`main`）、`some_string`（関数内の仮引数）、`s2_returned`（`main` の受け取り変数）は、関数呼び出しに伴いスタックフレームが独立して生成されるため、スタック上のアドレスはすべて異なる。
  - **ヒープデータの一貫性と所有権のリレー**:
    - 一方で、指しているヒープアドレスはすべて `0x1018719a0` で **完全に同一**。
    - 関数への引数渡しや戻り値の返却においても、重いヒープデータの再確保やコピーは一切行われず、スタック上のメタデータ（24バイト）のみを高速にムーブ（所有権の譲渡）していることが物理レベルで実証された。

### 2.6 [Drop検証] CustomDrop 構造体を用いたスコープ・ムーブ・早期解放の実証
- **検証コード**:
  ```rust
  struct CustomDrop {
      name: &'static str,
  }

  impl Drop for CustomDrop {
      fn drop(&mut self) {
          println!("[Drop] {} が解放されました", self.name);
      }
  }
  ```
- **実行結果**:
  ```text
  --- 5. 所有権のドロップ（Drop）とスコープ ---
  --- 内部スコープでの解放
  内部スコープに入りました
  c_inner.name = c_inner
  内部スコープから抜ける直前
  [Drop] c_inner が解放されました
  内部スコープから抜けた直後

  --- 所有権移動時の解放
  c_before_move.name = c_before_move
  c_before_moveの所有権をc_after_moveへ移動する直前
  c_before_moveからc_after_moveへの所有権移動の完了
  c_after_move.name = c_before_move

  --- 早期解放
  c_early_drop.name = c_early_drop
  c_early_dropを早期解放
  [Drop] c_early_drop が解放されました
  c_early_dropの解放完了
  [Drop] c_before_move が解放されました
  ```
- **実証できたこと**:
  1. **内部スコープの即時解放**:
     - `c_inner` は外側のスコープ終了を待たず、自身のブロックを抜けた瞬間（`内部スコープから抜けた直後` の手前）に確実に Drop される。
  2. **ムーブ時の Drop 対象の引き継ぎと二重解放防止**:
     - `c_after_move = c_before_move;` の実行後、元の変数 `c_before_move` の Drop は完全にキャンセル（除外）される。
     - 最後の `[Drop] c_before_move が解放されました` は、新しい所有者 `c_after_move` が `main` 関数の終端でスコープを抜けた際に **たった1度だけ** 実行されたもの。
     - これにより、ムーブによって変数は未束縛状態となり、所有権を引き継いだ新しい変数側でのみ Drop が行われることが実証された。
  3. **早期解放（`drop` 関数）**:
     - `drop(c_early_drop)` を呼び出したその行で即座に Drop が実行され、`c_early_dropの解放完了` より前に解放処理が完了することが確認された。
